---

Сервис принимает один GeoJSON конкурсной структуры (существующая тепловая сеть, камеры, источник,
точки подключения перспективных ОКС, пространственные ограничения) и автоматически строит до трёх
содержательно разных вариантов подключения всех точек ОКС: маршруты, места присоединения, новые
камеры, технические узлы, расходы, условные диаметры, проверку предельной длины по каждому пути,
стоимость строительства и ранжирование. Результат — GeoJSON по техническому приложению (редакция от 21.09.2026), раздел 7.

**Две геометрии на выбор — инженерная и кратчайшая.** Сетка поиска разворачивается на преобладающий
азимут существующей сети и застройки (на конкурсном наборе 69,1°, определяется автоматически).
*Инженерные* варианты идут длинными прямыми вдоль проездов: поворот на 45° штрафуется в десять раз
сильнее прямого угла, потому что поворот 90–130° работает как самокомпенсация температурных удлинений,
а при углах свыше 130° требуются неподвижные опоры. *Кратчайшие* варианты после поиска по сетке
спрямляются произвольным углом там, где прямая свободна: приложение в редакции от 21.09.2026 (§2.1)
допускает любой поворот до 90° включительно и не удорожает «нестандартные» углы. Повороты круче 90°
запрещены на уровне алгоритма — их не порождает ни поиск, ни спрямление. Ранжирование — по показателю S,
поэтому выбор между «красивой» и «короткой» трассой делает не разработчик, а формула техприложения.
Подробности — `docs/algorithm.md`, раздел 2а.

## Где сервис стоит в процессе техприсоединения

По регламенту подключения ПАО «МОЭК» (2025) после приёма заявки исполнитель «определяет техническую
возможность подключения, включая определение оптимальной точки присоединения» и мероприятия по подключению —
на это отведено до 20 рабочих дней рассмотрения заявки. Сервис автоматизирует именно этот шаг: по данным
о существующей сети (электронная модель, например ГИС CityCom «ТеплоГраф» МОЭК), пространственным
ограничениям (Сводный план подземных коммуникаций Москвы) и точкам присоединения из заявок (единое окно
mos.ru, ПП РФ № 955) он за секунды выдаёт варианты трассы, места присоединения и стоимость —
заготовку для условий подключения и согласования трассы в ГИС ОГД. Подробнее — `docs/ecosystem.md`.

В терминах отрасли: новая камера в точке присоединения = место присоединения к существующей сети;
«маршрут не найден» = отсутствие технической возможности подключения по технологическим коридорам
(ПП РФ № 2115, регламент МОЭК п. 1.4); радиус поиска места присоединения = радиус эффективного
теплоснабжения. Проверка резерва пропускной способности существующей сети в расчётной модели
приложения от 21.09.2026 не выполняется и остаётся за теплоснабжающей организацией.

## Стек (по ТЗ раздел 3)

Java 11 · Spring Boot 2.6.3 · Maven · PostgreSQL 14 · springdoc-openapi-ui 1.7.0 · JTS 1.19 · proj4j ·
docker-compose 1.29.2. Полностью офлайн, без обязательного UI.

Единый вход (Keycloak) и журнал событий — отдельный контур, см. «Доступ и журнал событий» ниже.
Оцениваемый запуск от них не зависит.

## Запуск

```bash
docker-compose up --build -d
# Swagger UI:  http://localhost:8080/swagger-ui.html   (OpenAPI JSON: /v3/api-docs)
```

Синхронный расчёт (файл → выходной GeoJSON одним запросом):

```bash
curl -F "file=@data/samples/contest_dataset.geojson" http://localhost:8080/api/process -o result.geojson
```

Асинхронный контур для больших файлов (до 3 ГБ, ТЗ 3.2):

```bash
curl -F "file=@input.geojson" http://localhost:8080/api/jobs          # → {"id": "...", "status": "QUEUED"}
curl http://localhost:8080/api/jobs/<id>                               # статус, время расчёта, лучший вариант
curl http://localhost:8080/api/jobs/<id>/result -o result.geojson      # выгрузка
curl http://localhost:8080/api/jobs/<id>/diagnostics                   # диагностика входных данных и расчёта
```

Другой ресурс (водоснабжение, кабельные линии) — сменой справочника, без правки кода:

```bash
HEATNET_RULES=./rules-profiles/water docker-compose up -d    # профиль-пример: водопровод
```

Проверяется тестом `ResourceProfileTest`: тот же конкурсный набор на справочнике водопровода —
34 участка, 1 960 м, S = 7,382. Подробности — `docs/limits.md`, раздел «Универсальность».

Число вариантов в выдаче: по умолчанию до трёх (ТП §2.8). Для сравнения стратегий на демонстрации —
`POST /api/process?variants=7`: считаются и отдаются все рассчитанные, в диагностику пишется пояснение.

Правила и справочники (табл. 4.1, 4.2, 5.1, 8.2, 8.3, 9 техприложения) лежат в
`src/main/resources/rules/*.yml`; свою копию можно положить в каталог `HEATNET_RULES` и перечитать
через `POST /api/rules/reload` — без перекомпиляции.

## Доступ и журнал событий

При включённом входе закрыто всё, кроме оболочки страницы и адреса провайдера: данные расчёта
(`/api/samples/*`), журнал, правила, Swagger и `/v3/api-docs` требуют токен, а веб-сервер витрины
статические образцы больше не раздаёт — их отдаёт сам сервис под теми же правилами доступа.
Просмотрщик в этом режиме встречает экраном входа.

**Журнал событий** ведётся всегда: приём файла, результат расчёта, ошибка валидации, задания очереди,
перечитывание правил, входы пользователей. Каждая запись содержит сквозной `X-Request-Id` (его можно
задать своим заголовком и сопоставить с логами интеграции), пользователя и роли, IP, длительность и
подробности в JSON. Хранится в PostgreSQL рядом с заданиями:

```bash
curl "http://localhost:8080/api/events?type=PROCESS_DONE&size=50"
curl  http://localhost:8080/api/events/stats
```

**Единый вход** выключен по умолчанию: конкурсный контур поднимается одним `docker-compose up` без
внешних систем, все методы открыты, в журнале `actor = anonymous`. В этом же режиме работает
демонстрационный стенд, чтобы решение можно было посмотреть без учётной записи. Включается оверлеем:

```bash
KEYCLOAK_PUBLIC_URL=http://<адрес стенда>:8081 \
docker-compose -f docker-compose.yml -f deploy/docker-compose.stand.yml -f deploy/docker-compose.keycloak.yml up -d --build
```

Realm `heatnet`, клиент `heatnet-viewer` (authorization code + PKCE), три роли и три пользователя
заводятся автоматически из `deploy/keycloak/realm-heatnet.json`, в админке настраивать нечего:

| Пользователь | Роль | Что может |
|---|---|---|
| `admin.heat` | `heatnet-admin` | всё, включая перечитывание правил |
| `engineer` | `heatnet-engineer` | запускать расчёты, читать журнал и правила |
| `viewer` | `heatnet-viewer` | только читать результаты и журнал (расчёт → 403) |

Пароль у всех — `heatnet`, консоль Keycloak — `admin/admin`. Сервис работает как resource server:
ключи проверки берутся по внутреннему адресу `keycloak:8080`, издатель проверяется по внешнему адресу
стенда (иначе контейнер не резолвит адрес, по которому браузер получил токен).

## Демонстрационный стенд

Развёрнут на сервере команды: **http://13.143.181.167/** — просмотрщик с загруженным конкурсным набором
и результатом; Swagger UI — http://13.143.181.167/swagger-ui.html; API — `http://13.143.181.167/api/...`.
Стенд поднят той же командой, что будет у жюри, на **docker-compose 1.29.2** и Ubuntu 22.04
(6 ядер, 16 ГБ). Витрина на nginx добавляется отдельным файлом и в оцениваемый контур не входит:

```bash
docker-compose up -d --build                                                  # оцениваемый сервис (app + db)
docker-compose -f docker-compose.yml -f deploy/docker-compose.stand.yml up -d # + витрина на порту 80
```

**Совместимость docker-compose 1.29.2.** Требуемая ТЗ версия — из 2021 года. На чистой машине
`docker-compose up -d --build` отрабатывает полностью (проверено на Ubuntu 22.04 c Docker 29.8).
Если на стенде уже остались контейнеры прошлого запуска, compose 1.29.2 на новых версиях Docker падает
при их пересоздании с `KeyError: 'ContainerConfig'` — это ограничение самого compose v1, а не сервиса.
Лечится одной командой перед запуском:

```bash
docker-compose down          # либо: docker rm -f heatnet_app_1 heatnet_db_1
docker-compose up -d --build
```


## Структура

| Пакет | Назначение |
|---|---|
| `ingest` | потоковый парсер GeoJSON (Jackson streaming), валидация и диагностика входа |
| `network` | топология существующей сети: цепочка к источнику по `upstream_object_id` или по геометрии |
| `routing` | поле препятствий по табл. 5.1, растровое окно, A* по 8 направлениям (повороты не круче 90°), упрощение ломаной и спрямление произвольным углом |
| `planner` | выход из ОКС по нормали, стратегии вариантов, сборка дерева новой сети, проверка отступов по фактическому ДУ |
| `events` | журнал событий в PostgreSQL, сквозной `X-Request-Id`, REST `/api/events` |
| `security` | resource server для токенов Keycloak; по умолчанию выключен |
| `hydraulics` | расходы по дереву, подбор ДУ по расходу и предельной длине, техузлы, камеры и врезки |
| `export` | выходной GeoJSON строго по ТП §10 |
| `jobs`, `api` | очередь расчётов в PostgreSQL, REST и Swagger |

Описание алгоритма, выходных данных, границ применения и дополнительной задачи по глубине — в `docs/`.

## Просмотр результата

`viewer/index.html` — статическая страница (Leaflet, работает офлайн): шапка сервиса с переключателем
фирменного стиля (ДИТ / МОЭК) и вкладками **Карта · Варианты · Журнал событий · Правила расчёта · О сервисе**.
Перетащите входной датасет и файл результата, переключайте варианты, смотрите сводку и атрибуты объектов.
Компас в углу карты — переключатель режима поворота: нажали, покрутили карту мышью на любой угол,
нажали ещё раз — угол зафиксирован (двойной клик — возврат на север). Наведение на элемент трассы
показывает его стоимость, клик закрепляет карточку с разбором: диаметр, длина, расход, способ прокладки,
удельная стоимость за метр и доля в итоговой стоимости варианта.
Если запустить `python3 -m http.server` из корня репозитория и открыть `http://localhost:8000/viewer/`,
образцы из `data/samples/` подхватятся автоматически. Просмотрщик не входит в оцениваемый сервис.

Режим с учётом глубины: `curl -F "file=@input.geojson" "http://localhost:8080/api/process?depth=true" -o result_depth.geojson`.
