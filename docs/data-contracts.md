# Контракты данных

Что сервис принимает и что отдаёт. Обе стороны описаны машиночитаемыми схемами — результат и
входной файл можно проверить, не запуская сервис.

| Сторона | Схема | Отдаётся сервисом |
|---|---|---|
| Вход | [schema/input.schema.json](schema/input.schema.json) | — |
| Выход | [schema/result.schema.json](schema/result.schema.json) | `GET /api/schema/result` |

```bash
check-jsonschema --schemafile docs/schema/input.schema.json  input.geojson
check-jsonschema --schemafile docs/schema/result.schema.json result.geojson
```

## Вход

GeoJSON `FeatureCollection` в EPSG:4326. Обязателен хотя бы один объект `oks_connection_point` —
без точек присоединения считать нечего.

| Объект | `object_type` | Геометрия | Обязательные атрибуты | Что делает сервис, если чего-то нет |
|---|---|---|---|---|
| Источник теплоснабжения | `source` | Point | `id` | без источника расчёт идёт, но цепочка к источнику не определяется |
| Существующая тепловая сеть | `heat_network` | LineString | `id`, `diameter` | нет `flow_tph` — текущий расход принимается нулевым с предупреждением; нет `upstream_object_id` — направление к источнику восстанавливается по геометрии |
| Существующая тепловая камера | `heat_chamber` | Point | `id` | нет `diameter` — берётся наибольший из примыкающих участков |
| Точка присоединения ОКС | `oks_connection_point` | Point | `id`, `flow_tph` | без `flow_tph` точка пропускается с ошибкой в диагностике |
| Пространственное ограничение | `restriction` | любая | `id`, `restriction_type` | неизвестный вид обрабатывается правилом по умолчанию (запрет прохода, отступ 1 м) и попадает в диагностику |

Что сервис прощает: перепутанный порядок объектов, отсутствие необязательных атрибутов, невалидную
геометрию отдельных объектов, посторонние свойства, точку присоединения внутри своего здания,
числовые и строковые идентификаторы вперемешку. Всё это становится диагностикой, а не отказом.

Что сервис не прощает: файл не GeoJSON, отсутствие точек присоединения, расход, который не удаётся
прочитать как число. Ответ — 422 с перечнем: какой объект и чем не подошёл.

## Выход

GeoJSON `FeatureCollection` в EPSG:4326 по разделу 7 приложения. Состав объектов и атрибутов —
в [output.md](output.md), полный разбор дополнительных полей — там же.

| Объект | `object_type` | Геометрия |
|---|---|---|
| Участок новой сети | `heat_network` | LineString |
| Новая тепловая камера | `heat_chamber` | Point |
| Технический узел | `technical_node` | Point |
| Сводка варианта | `variant_summary` | null |

Дополнительные поля сверх обязательного состава (раздел 7 их допускает): пояснения к варианту,
метод поиска и время по этапам, метрики геометрии, влияние на существующую сеть, пересечения
по глубине, пометки о ручной проработке. Проверка обязательной части их игнорирует.

В корне файла — блок `metadata`: SHA-256 входного файла, число объектов на входе, время расчёта,
режим глубины, выбранные методы, редакция приложения и проекции. По нему видно, из каких данных
и какой редакцией правил получен результат.

## Совместимость

* Тип идентификатора сохраняется: если во входных данных `id` был числом, в выходе он тоже число.
* Идентификаторы выходных объектов уникальны во всём файле и содержат номер варианта
  (`v1_seg_3`, `v1_ch_4`, `v1_node_2`).
* `start_node_id` и `end_node_id` ссылаются на точку присоединения, существующую или новую камеру
  либо технический узел и совпадают с геометрическими концами линии.
* Длины и стоимости считаются по горизонтальной проекции в EPSG:32637 — так же, как их пересчитывает
  независимый валидатор.
