# Куда встраивается сервис: экосистема техприсоединения в Москве

Схема (слева направо):

```
Заявка застройщика ──► mos.ru «Единая заявка на подключение к сетям ИТО» (ДИТ, ПП РФ № 955)
                                 │ точки присоединения, нагрузки (Гкал/ч → т/ч)
                                 ▼
   ГИС CityCom «ТеплоГраф» ──► ЦАТ ◄── Сводный план подземных коммуникаций (Москомархитектура, Мосгоргеотрест)
   (ПАО «МОЭК»: участки, ДУ,      │        (здания, дороги, ж/д, вода, газ, кабели, глубины; МСК-77 → UTM 37N)
    расходы, камеры, ЦТП)         │
                                 ▼
          варианты подключения: трассы, места присоединения, новые камеры, стоимость, S
                                 │
                 ┌───────────────┼──────────────────────┐
                 ▼               ▼                      ▼
   ООО «ЦТП МОЭК»: условия   ГИС ОГД Москвы:        Цифровой двойник Москвы:
   подключения, мероприятия  согласование трассы    слой новой сети с Z
   и плата (ставки ДЭПиР)    инженерных коммуникаций
```

## Роли

| Участник | Роль в процессе | Связь с сервисом |
|---|---|---|
| Застройщик (заявитель) | подаёт заявку с тепловой нагрузкой, границей участка | точка присоединения на границе участка (`oks_connection_point`) |
| ДИТ Москвы | оператор mos.ru и городских ИС, единое окно техприсоединения, данные о резервах мощности | владелец сервиса; сводит заявки по всем ресурсам |
| ПАО «МОЭК» / ООО «ЦТП МОЭК» | единая теплоснабжающая организация: техническая возможность, оптимальная точка присоединения, мероприятия, договор (20 раб. дней), подключение (18 мес.) | потребитель результата; источник электронной модели сети |
| Москомархитектура, ГБУ «Мосгоргеотрест» | Сводный план подземных коммуникаций (>130 тыс. км), ГИС ОГД, согласование трасс | источник ограничений; приёмник трассы на согласование |
| ДЖКХ Москвы | схема теплоснабжения: радиусы эффективного теплоснабжения, перспективные нагрузки | параметр радиуса поиска места присоединения |
| ДЭПиР Москвы | ставки платы за подключение по диаметрам и типу прокладки | справочник стоимости (точка расширения `laying_cost_factors`) |
| Региональный центр компетенций по техприсоединению (меморандум 05.06.2026) | магистральные сети, приоритизация подключений, сокращение сроков | массовый расчёт вариантов подключения |

## Соответствие терминов

| В выходном GeoJSON (ТП §10) | В регламенте МОЭК / ПП РФ № 2115 |
|---|---|
| `heat_chamber` в точке присоединения | место присоединения к существующей тепловой сети (отдельного объекта приложение не предусматривает) |
| `oks_connection_point` | точка подключения на границе земельного участка объекта |
| `existing_chamber_tie_in_count` в сводке | врезки в существующие тепловые камеры, 5 млн ₽ за каждый входящий участок |
| `unconnected_oks_ids` | отсутствие технической возможности подключения по технологическим коридорам — ручная проработка |
| `calculated_cost` | оценка стоимости мероприятий (не плата за подключение по тарифу) |
| `candidate_radius_m` | радиус эффективного теплоснабжения |

## Доступ, роли и разграничение видимости

**Техническое задание авторизацию не требует** — в нём есть только требование выдерживать работу
до 50 пользователей (раздел 3.2). Мы добавили единый вход не потому, что он обязателен для сдачи,
а потому что без него сервис нельзя ввести в эксплуатацию: расчёт подключений — это персональные
данные заявителей, коммерческие условия и решения, влияющие на деньги, поэтому нужно знать, кто
именно запускал расчёт и что ему было позволено.

### Что сделано сейчас

Сервис принимает токены внешнего поставщика удостоверений (проверено на Keycloak) и разбирает роли
из них. В поставке — готовый realm, который разворачивается из файла: три роли и три учётные записи,
настраивать в админке нечего.

| Роль | Что разрешено |
|---|---|
| `catp-admin` | расчёты, правка и перечитывание правил, журнал событий |
| `catp-engineer` | запуск расчётов, просмотр результатов, журнала и правил |
| `catp-viewer` | только просмотр результатов и журнала; запуск расчёта — отказ 403 |

Каждое действие пишется в журнал с именем пользователя, его ролями, адресом и сквозным
идентификатором запроса. Режимов доступа три: `off` — открыто (так работает конкурсная проверка),
`optional` — вход доступен, но не обязателен (так работает демонстрационный стенд),
`required` — без токена доступа нет.

### Что даёт Keycloak как целевое решение

Выбор именно этой платформы означает, что дальнейшие требования безопасности закрываются
настройкой, а не доработкой сервиса:

- **Собственное хранилище учётных записей** — логины, пароли, политики сложности и срока действия,
  блокировка после неудачных попыток, самостоятельное восстановление пароля.
- **Корпоративный вход без отдельного пароля (SSO)** — подключение к Active Directory или LDAP
  организации, вход по доменной учётной записи, единая сессия с другими системами заказчика.
  Сотруднику не нужен ещё один пароль, а увольнение закрывает доступ во всех системах сразу.
- **Двухфакторное подтверждение** — одноразовый код в приложении-аутентификаторе, по СМС или
  аппаратный ключ; включается для отдельных ролей, например только для администраторов.
- **Федерация с государственными системами** — при необходимости вход через ЕСИА или ведомственный
  провайдер подключается как ещё один источник удостоверений.
- **Управление сессиями** — принудительное завершение сеанса, ограничение времени жизни токена,
  отзыв доступа у конкретного сотрудника без перезапуска сервиса.
- **Аудит со стороны провайдера** — попытки входа, смены пароля и прав фиксируются отдельно от
  журнала сервиса, что важно при разборе инцидентов.

### Разграничение видимости по подчинённости

Целевая модель — не только «что можно делать», но и «чьи расчёты видно». Организационная структура
описывается в Keycloak группами, и права наследуются по дереву подразделений:

| Кто | Что видит в перечне расчётов |
|---|---|
| Специалист | только свои расчёты |
| Начальник отдела | свои и расчёты сотрудников своего отдела |
| Заместитель генерального директора | расчёты всех подчинённых подразделений |
| Администратор | все расчёты организации |

Со стороны поставщика удостоверений это готовая возможность: группы вкладываются друг в друга,
сотрудник включается в свою группу, а в токен добавляется его подразделение и цепочка вышестоящих.
Со стороны сервиса для этого нужно хранить у каждого задания владельца и его подразделение и
фильтровать перечень заданий по этим полям — задел уже есть: журнал событий и задания пишут имя
пользователя и его роли, добавить фильтр по подразделению можно без изменения расчётной части.

В текущей версии разграничение работает на уровне ролей, иерархия подразделений не включена:
конкурсная проверка запускает сервис без внешних систем, и проверить эту часть эксперту было бы
не на чем.

## Встраивание в контур заказчика

| Задача интеграции | Как решено |
|---|---|
| единый вход сотрудников | сервис принимает JWT внешнего провайдера (проверено на Keycloak: realm `ЦАТ`, роли `ЦАТ-admin` / `ЦАТ-engineer` / `ЦАТ-viewer`, поток authorization code + PKCE). Провайдер заменяется настройкой issuer и адреса ключей — код не меняется |
| разграничение прав | запуск расчёта и перечитывание правил — инженеру и администратору, чтение результатов и журнала — всем ролям |
| прослеживаемость | журнал событий в БД: кто, когда, какой файл, сколько считалось, чем закончилось; сквозной `X-Request-Id` связывает запись с логами вызывающей системы |
| мониторинг | `GET /api/events/stats` — сводка по видам событий; время расчёта в заголовке `X-Compute-Millis` |

Для конкурсной проверки вход выключен: сервис поднимается одним `docker-compose up` и не зависит
от внешних систем.

## Было / стало

Сегодня определение технической возможности и оптимальной точки присоединения входит в 20 рабочих дней
рассмотрения заявки и выполняется инженером вручную по материалам Сводного плана и модели сети. Сервис
даёт ранжированные варианты со стоимостью за секунды (конкурсный набор из 17 точек — 10 с на шести
ядрах для лучшего варианта, 41 с на все семь стратегий), а инженер тратит время на проверку и выбор, а не на построение.

Реконструкция существующей сети в расчётной модели приложения от 21.09.2026 не выполняется, поэтому
проверка резерва пропускной способности остаётся за ресурсоснабжающей организацией.
