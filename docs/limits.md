# Границы применения решения

**Что решение делает.** Предварительная (предпроектная) трассировка новой тепловой сети в плане
по формализованным правилам технического приложения (редакция от 21.09.2026): выбор мест
присоединения, объединение точек подключения, расходы, ДУ, предельные длины по каждому пути,
стоимость строительства и ранжирование вариантов.

**Допущения и ограничения.**
1. Двумерная модель: глубина, продольный профиль, рельеф не учитываются (обязательная часть ТЗ 2.2).
   Режим с учётом глубины — отдельная дополнительная задача.
2. Гидравлика упрощена до пропускной способности и предельной длины по ДУ (ТП §2.3, табл. 1);
   давление, потери напора, насосные режимы не считаются (ТЗ 2.12). Реконструкция существующей сети
   и резерв её пропускной способности в расчётной модели не определяются (ТП §2.4).
3. Точность геометрии — шаг растровой сетки (2 м по умолчанию): трасса проходит по узлам сетки,
   развёрнутой на азимут застройки. В инженерных вариантах повороты кратны 45°, в спрямлённых угол
   произвольный, но не круче 90° (ТП §2.1). Поиск оценивает отступы по центрам клеток, поэтому
   фактический зазор может отличаться от нормативного на величину до половины шага; готовая трасса
   перепроверяется по фактическим диаметрам (`CLEARANCE_OK` / `CLEARANCE_TIGHT`, см. algorithm.md 5а).
   Для более точного результата шаг уменьшается в `rules/routing.yml` ценой времени расчёта.
4. Ось полигонального препятствия (дорога, ж/д) строится как длинная сторона минимального
   охватывающего прямоугольника; для сильно изогнутых полигонов угол пересечения оценивается
   приближённо. Для линейных объектов угол считается к ближайшему прямому отрезку.
5. Существующая сеть по геометрии не проверяется (Q&A); при отсутствии `flow_tph` текущий расход
   принимается 0, при отсутствии `upstream_object_id` цепочка восстанавливается по совпадающим концам
   участков (допуск 0,5 м) — расхождения фиксируются в диагностике.
6. Азимут сетки определяется по существующей сети: если в наборе она короткая или разнонаправленная,
   разворот сетки теряет смысл — тогда его задают вручную параметром `grid_bearing_deg`.
   Стоимость присоединения (камера или врезка) учитывается в поиске как терминальная стоимость цели.
7. Совместное подключение — жадная последовательная стратегия (ближние точки формируют ствол),
   а не глобальная оптимизация дерева Штейнера; варианты дают альтернативы, но оптимальность
   в строгом смысле не гарантируется.
8. Типы ограничений, отсутствующие в правилах, обрабатываются по правилу по умолчанию (запрет с
   отступом 1 м) с предупреждением. Правило для `railway` принято как для трамвайных путей, угол
   пересечения ужесточён до 60° по СП 124.13330 — допущение до уточнения постановщиком.
9. Отступ от ОКС при поиске берётся по верхней оценке ДУ новой сети (ДУ для суммарного расхода всех
   точек расчёта, поднятый на ступень) — консервативно, потому что фактический диаметр участка
   известен только после гидравлики. Из-за этого распределительные ветки малого ДУ обходят здания с
   запасом; точный двухпроходный пересчёт зон по фактическим диаметрам не выполняется, вместо него
   сделана проверка результата.
10. Один источник, один экземпляр сервиса; распределённый расчёт не предусмотрен (ТЗ 2.2, Q&A).
11. Входной файл обрабатывается потоково; для больших наборов включается двухпроходное чтение с
    фильтром по области расчёта (см. README, «Большие файлы»). В памяти остаются только объекты,
    способные повлиять на трассу: на наборе 3,05 ГБ это 349 объектов из 1 487 256, расчёт занимает
    188 с и 5,9 ГБ. Ограничение подхода: если точки присоединения разнесены по всему городу,
    область расчёта охватит его целиком, и фильтр перестанет помогать — тогда потребуется дисковое
    хранилище объектов (PostGIS) либо разбиение задания по кварталам.
12. Единый вход и роли (Keycloak) — отдельный контур: по умолчанию проверка токенов выключена,
    и сервис принимает запросы без аутентификации, как требует конкурсная проверка. Журнал событий
    при этом ведётся всегда, действия записываются от имени `anonymous`.

**Универсальность.** Тип ресурса не зашит в код: справочник ДУ/пропускной способности/цен и правила
пересечений — конфигурация, поэтому та же логика применима к водопроводу, канализации, кабельным
линиям при замене справочников (Q&A: критерий дополнительной оценки).

Это не декларация: в репозитории лежит готовый профиль `rules-profiles/water` (хозяйственно-питьевой
водопровод) и тест `ResourceProfileTest`, который прогоняет на нём **тот же конкурсный набор тем же
алгоритмом**, без единой правки кода:

```bash
HEATNET_RULES=./rules-profiles/water docker-compose up -d     # или POST /api/rules/reload
```

Результат прогона: 34 участка, 1 960 м, 53 633 940 ₽, S = 7,382; расходы интерпретируются в м³/ч,
диаметры берутся из ряда ПЭ-труб (63…500), узел ветвления — водопроводный колодец, обычная глубина
2,0 м ниже промерзания. Тип ресурса виден в диагностике (`RESOURCE`) и в статистике (`resource`).

Числа в профиле водопровода — **ориентировочные, для демонстрации механизма**: перед применением их
заполняет профильный специалист по СП 31.13330 и СП 42.13330, поле `source` у каждого правила для
этого и предусмотрено. Проверено именно то, что от типа ресурса не зависит ни одна строка кода:
трассировка, сборка дерева, подбор диаметра по расходу и предельной длине, узлы, стоимость и
ранжирование работают на любом справочнике той же структуры.
